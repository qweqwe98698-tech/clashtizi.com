> **【💡 30 秒极速分诊：Clash Verge Rev 节点全红到底是什么问题？】**
> - **第一核心定性**：**“节点全部超时 (All Timeout)”绝不等于“机场跑路”！** 只有少数节点红，优先查单条线路；若所有地区所有节点在同一瞬间全部标红，90% 是**“本地系统时间偏差 > 60秒（导致 TLS 握手彻底失败）”**、**“本地宽带物理断网”**或**“Mihomo 底层内核异常挂起”**；
> - **四种高频现象极速诊断**：
>   1. **所有节点同一瞬间全红** ──► 优先校准 Windows/Mac 系统时间至北京时间毫秒级；
>   2. **同地区节点红，其他地区绿** ──► 该区域机房中转入口故障，切其他国家节点使用；
>   3. **节点测试全红但网页正常打开** ──► 客户端配置的【测速 URL】被墙，真实节点通道完好；
>   4. **节点显示绿色数字但打不开网页** ──► 节点通畅，问题出在【系统代理】开关或分流规则。

## 一、单节点 vs 全部节点 Timeout 核心排查总表

在排障时，必须先通过故障范围缩小问题层级：

| 故障范围表现 | 底层真实技术含义 | 最核心诱发诱因 | 第一步标准应对动作 |
| :--- | :--- | :--- | :--- |
| **仅单个节点显示 Timeout** | 该台海外后端服务器宕机或维护 | 单机硬件故障、机房 IP 被流媒体封锁 | 切换到同策略组下的其他备用节点 |
| **同一国家/地区节点全红** | 该地区在中转机房的入口线路断流 | 跨境海缆故障、专线入口服务器断电 | 临时改用其他地区的节点出站 |
| **所有地区、所有节点全部全红** | 全局性系统级故障，共同依赖中断 | **系统时间不同步**、本地断网、Core 崩溃 | 校准北京时间，检查宽带，重启 Core |
| **测速显示红色，但网页能正常开** | 延迟测试请求受阻，但代理通道完好 | 配置文件中的 `test-url` 地址不可达 | 修改测试网址为 `http://www.gstatic.com/generate_204` |
| **测速显示绿色，但网页完全打不开** | 节点网络通畅，流量未进入代理内核 | 系统代理未开、7890 端口冲突、分流规则阻断 | 检查系统代理开关，查看 Connections 面板 |

## 二、双网络路径辨析：为什么“订阅能更新，但节点全红”？

很多用户遇到“订阅明明能刷新，为什么测速全红”时百思不得其解：

```text
 ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
 │                               【订阅获取路径 vs 节点连接路径】                              │
 ├─────────────────────────────────────────────────────────────────────────────────────────────┤
 │ 【路径 1：订阅拉取】                                                                        │
 │ Clash Verge Rev 客户端 ──► HTTPS ──► 机场网站 Web 服务器 ──► 下载 Profile 文本 (国内即可直连)│
 ├─────────────────────────────────────────────────────────────────────────────────────────────┤
 │ 【路径 2：节点连接】                                                                        │
 │ Mihomo 底层内核 ──► 专线隧道 ──► 境外海外代理节点 ──► 访问 Google/YouTube (受出口防火墙监管) │
 └─────────────────────────────────────────────────────────────────────────────────────────────┘
```

> **💡 核心真相**：订阅服务器是用来存放配置文件的普通网站，而节点是用来翻墙的高性能转发中转机，两者**完全是两套不同的服务器与网络路线**。订阅更新成功只能证明机场网站活着，不能证明节点服务器通畅。

## 三、全节点标红的“隐形杀手”：系统时间与 TLS 证书握手

在所有节点同时标红的故障中，**有超过 60% 是系统时间误差导致的**：

```text
 1. 【TLS 证书时效严格校验】：
    - 现代节点协议（Shadowsocks-2022、VLESS、Hysteria 2、TUIC v5）均高度依赖双向 TLS/AEAD 加密通信；
    - 加密握手协议强制要求客户端本地时间与服务端时间误差【不得超过 60~90 秒】；
    - 若电脑主板电池老化或长久未联网导致系统时间慢了几分钟，客户端会判定服务端证书“尚未生效”或“已经过期”，直接在底层掐断连接并显示 Timeout。

 2. 【极速修复操作】：
    - Windows：右键右下角任务栏时间 ──►【调整日期和时间】──► 点击【立即同步】；
    - macOS：进入【系统设置】──►【通用】──►【日期与时间】──► 开启“自动设置日期与时间”。
```

## 四、深入理解 URL-Test：延迟数字（ms）到底代表什么？

初学者最常犯的错误，就是把 Clash 的延迟测试当成“下载测速”：

```text
 ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
 │                               【URL-Test 延迟 vs ICMP Ping 区别】                           │
 ├──────────────────────┬──────────────────────────────┬───────────────────────────────────────┤
 │ 比较维度             │ URL-Test (Clash Verge Rev 测速)│ 传统 ICMP Ping (网络诊断命令)        │
 ├──────────────────────┼──────────────────────────────┼───────────────────────────────────────┤
 │ **测试层级**         │ 属于应用层 HTTP/HTTPS 握手   │ 属于底层网络层 ICMP 协议              │
 │ **测试过程**         │ 模拟向目标网址发请求并收到应答| 仅计算数据包往返时间                  │
 │ **代理支持**         │ 能够真实反映节点是否可用     │ 很多中转机屏蔽 ICMP，Ping 绿不代表能连│
 │ **速率代表性**       │ 仅反映连接响应快慢，不代表带宽| 仅反映物理距离，不代表吞吐量          │
 └──────────────────────┴──────────────────────────────┴───────────────────────────────────────┘
```

### 为什么“20ms 的节点可能比 120ms 的节点还要慢”？
- **20ms 香港节点**：可能物理距离近但服务器只有 10Mbps 共享小带宽，晚高峰严重拥堵丢包；
- **120ms 美国节点**：虽跨洋延迟稍高，但拥有 10Gbps 独享国际带宽，看 4K 视频秒开加载；
- **选节点黄金法则**：日常办公和网页浏览选低延迟节点，看高清视频和大文件下载优先看节点带宽与专线稳定性。

## 五、Mihomo Core 运行状态与日志排查

节点测试是由底层 Mihomo Core 执行的，若 Core 假死，所有节点将直接不可测：

```text
 1. 【检查内核运行状态】：
    - 打开左侧导航栏的【设置 (Settings)】面板；
    - 查看【Mihomo 内核】或【Core 状态】是否正常点亮；若提示未启动，点击右侧的重启图标。

 2. 【通过日志面板捕获真实报错】：
    - 点击左侧【日志 (Logs)】面板，再次点击 Proxies 页面的测速闪电；
    - 查看日志窗口弹出的红色错误信息：
      - 若显示 `certificate has expired or is not yet valid` ──► 100% 为系统时间偏差；
      - 若显示 `dial tcp: i/o timeout` ──► 本地网络被阻断或节点 IP 离线；
      - 若显示 `dns resolve failed` ──► 节点域名解析失败，需配置本地 DNS。
```

## 六、多网卡与双 VPN 软件冲突排查

如果你近期在电脑上安装了其他代理或网络工具：

```text
 1. 【本地端口冲突（7890/7897 争抢）】：
    - 若后台同时开着 v2rayN、sing-box、旧版 CFW 或某些杀毒软件自带的加速器；
    - 两个客户端争抢同一个本地代理端口，将导致 Mihomo 无法绑定端口并引发节点测速假死；
    - 解决：彻底退出其他代理软件，重启电脑。

 2. 【多 TUN 虚拟网卡死锁】：
    - 两个软件同时创建虚拟网卡抢占 0.0.0.0/0 默认路由，导致底层数据包陷入死锁黑洞；
    - 解决：在设置中关闭其他软件的 TUN 网卡，或在适配器管理中禁用多余的虚拟网卡。
```

## 七、节点全部 Timeout 5 分钟极速排障 SOP（标准 HowTo）

遇到节点一瞬间全部标红时，请严格按以下 6 步标准顺序排查：

```text
 Step 1: 毫秒级校准系统时间 ──► 进入系统设置点击【立即同步】，确认时间与北京时间完全一致
    ↓
 Step 2: 验证物理网络连通性 ──► 断开 Wi-Fi 换手机 4G/5G 热点测试（排除光猫断网或路由器拦截）
    ↓
 Step 3: 重启 Mihomo 底层内核 ──► 在设置面板中重启 Core，或托盘右键彻底退出客户端重新启动
    ↓
 Step 4: 查看日志定位错误码 ──► 打开 Logs 面板重新测速，根据日志判断是 DNS、TLS 还是 Timeout
    ↓
 Step 5: 验证机场服务端状态 ──► 登录机场官方网站，查看最新系统公告确认是否全线机房割接维护
    ↓
 Step 6: 刷新或重新导入订阅 ──► 在 Profiles 页面右键卡片点击刷新，获取最新的可用节点列表
```

## 八、关于节点 Timeout 的 15 大核心认知误区

```text
 ❌ 误区 1：只要节点测速全部标红，就 100% 肯定买的机场彻底跑路了。(错！大半是本地系统时间慢了几分钟)
 ❌ 误区 2：URL-Test 延迟测试就是平常大家说的 cmd ping 命令。(错！URL-Test 是应用层 HTTP 握手测试)
 ❌ 误区 3：节点测速必须找延迟最小的（比如 10ms），用它上网一定最快。(错！延迟小不等于下载带宽大)
 ❌ 误区 4：节点显示 Timeout 说明节点服务器物理硬件一定烧毁了。(错！中间网络丢包超阈值即报超时)
 ❌ 误区 5：只要节点变红，就应该立刻把电脑所有防火墙和杀毒软件全部彻底关闭。(错！引狼入室且无用)
 ❌ 误区 6：节点全红时，反复疯狂点击右上角的测速闪电能把它“冲绿”。(错！频繁测速会触发服务器 WAF 防刷封锁)
 ❌ 误区 7：订阅更新成功就能保证节点一定全绿能用。(错！订阅是 Web 接口，节点是中转出口，路径完全独立)
 ❌ 误区 8：把代理模式切成 Global 全局模式，节点就会自动从红变绿。(错！Global 影响分流，不影响测速)
 ❌ 误区 9：节点测速全绿就证明电脑上的浏览器一定能翻墙上网。(错！系统代理未开或规则错误依然打不开网页)
 ❌ 误区 10：为了修复节点超时，必须在电脑里永久关闭 IPv6 协议栈。(错！双栈网络规范配置可完美共存)
 ❌ 误区 11：在两台电脑上同时使用同一个节点的测试结果一定完全相同。(错！不同电脑网络环境与系统时间各异)
 ❌ 误区 12：看到节点全红第一反应立刻把客户端卸载重装。(错！重装只会丢失配置，解决不了网络或时间问题)
 ❌ 误区 13：节点测试显示的超时时间（比如 5000ms）改得越大，节点就越稳定。(错！过大超时只会让选点迟钝)
 ❌ 误区 14：只要把所有节点写成 Direct 直连，测速就会变成 1ms。(错！Direct 不走节点，完全失去翻墙功能)
 ❌ 误区 15：企业内网里节点全红是因为机场服务器差。(错！企业防火墙网关严密阻断了常见外部代理端口)
```

## 九、常见问题解答 (FAQ)

### Q1：为什么所有节点在同一秒全部变成红色 Timeout 了？
**答**：所有节点同时超时，90% 是本地原因：请首先检查电脑系统时间是否准确同步（误差超过 60 秒会导致 TLS 握手失败）；其次检查本地宽带是否欠费断网，或重启客户端底层内核。

### Q2：URL-Test 延迟测试到底代表什么？它是 Ping 吗？
**答**：不是。URL-Test 是客户端向特定网址发起 HTTP 握手并测算响应时间的测试；它不仅测试了网络通畅，还验证了协议握手有效性，比单纯的底层 ICMP Ping 更能真实反映节点可用性。

### Q3：为什么 30ms 的香港节点看视频卡，130ms 的美国节点看 4K 却秒开？
**答**：因为 30ms 仅代表延迟低、响应快；而 4K 视频加载依赖的是节点的带宽吞吐量。若香港节点处于晚高峰拥堵，其实际带宽远不如空闲的千兆美国专线节点。

### Q4：为什么节点测速全是红色，但我访问 Google 和 YouTube 却完全正常？
**答**：说明节点本身完好！测速标红是因为客户端内置的“测速测试网址 (Test URL)”被本地阻断了；进入设置将测试网址替换为 `http://www.gstatic.com/generate_204` 即可恢复绿显。

### Q5：节点全部显示绿色数字，但为什么浏览器就是打不开任何海外网站？
**答**：测速绿仅代表节点与服务器通路正常。打不开网页通常是因为操作系统的【系统代理 (System Proxy)】未开启，导致浏览器数据没送进客户端；进入设置检查系统代理开关即可。

### Q6：为什么订阅更新明明提示成功，但节点依然全部 Timeout？
**答**：因为订阅更新连接的是机场的配置分发网站（国内通常可直连），而节点连接的是境外的代理中转机；两者网络路径完全不同，订阅成功不能代表节点活着。

### Q7：什么是“系统时间误差导致全节点红”？怎么一键解决？
**答**：现代加密协议强制要求时间同步以防重放攻击。右键点击电脑任务栏右下角时间，进入时间设置点击【立即同步】，将时间精确同步至北京时间，即可瞬间恢复节点。

### Q8：同一个地区（比如所有日本节点）全红，但香港节点全绿怎么办？
**答**：说明该机场的日本机房中转入口遭遇了网络抖动或正在维护割接。直接在代理页面将策略组手动切到绿色的香港或新加坡节点，不影响日常翻墙使用。
